视觉侧此前独立拟过一份 16 字节提案，与主控已实现代码在字节数、帧头、量纲、超时和命令结构上均不一致。主控的解析代码已写入固件，再并行一套会让硬件接线和联调各对两遍。该 16 字节提案作废，相关历史记录已标为 superseded。

## 1. 已完成的核对

- 用主控提供的 `../control/tools/protocol_example.py` 复算协议草案文档中的 3 个样例帧：

| 样例 | 结果 |
| --- | --- |
| `path_valid`（seq1、置信度 80、处理 20ms） | 逐字节一致 |
| `start`（命令 seq1） | 逐字节一致 |
| `stop`（命令 seq2） | 逐字节一致 |

- CRC-16/CCITT-FALSE 与标准向量 `123456789` → `0x29B1` 一致。视觉侧原提案使用同一算法，只是计算范围从 0–13 变为 0–17、低字节先发。
- 物理层一致：115200、8N1、3.3V TTL、TX/RX 交叉、共地、不传整幅图像。
- 端口：视觉侧按 `../control/docs/pin_plan.md` 的候选 USART2 / PA2 / PA3 准备，实物排针引出情况待硬件核对（见 `PROGRESS_2026-11-02.md` 第 6 节第 5 条）。

## 3. 视觉侧新增的硬约束

主控的 START / RUNNING 条件把 `processing_ms` 变成性能门槛，不只是统计字段：

- START 成功要求：已有有效路径 **且** 置信度 ≥ 40 **且** `processing_ms` ≤ 100ms **且** 本地路径年龄 < 200ms。
- RUNNING 中：`processing_ms` 超过 100ms 的帧不能用于启动或保持运行；收到新的无效或低质量路径立即 FAULT，左右请求归零；恢复数据不自动启动。

因此视觉侧必须实测每帧处理耗时并保证 < 100ms。当前已知：相机 320×240 约 57fps（≈17.5ms/帧），但检测部分耗时**尚未在板子上运行过**，100ms 预算目前是未知数，不能视为已达标。

主控文档也写明 200ms / 100ms / 40 及转向比例均为待实测参数，不能据此认定实车已停稳。

## 5. 视觉侧先决阻塞（非协议问题）

桌面 328 帧实测：一条车道边界出现率 **81%**，第二条只有 **2%**。140mm / 下俯 25° 安装位使远侧黑边在 y≈120 以下进不了画面。

这决定 `error` 与 `bend` 能否稳定给出。需硬件与主控在以下两者间决定：

- A：加高或减小俯角让两条边界同框（受整机高 ≤180mm 约束）；
- B：接受单边，按 `PORTING_REVIEW.md` 用已标定的每行车道宽度短时估计中线并明确降低置信度。

该决定不做，协议对齐也无法产生可用数据。已登记为状态表 `D-09`。
