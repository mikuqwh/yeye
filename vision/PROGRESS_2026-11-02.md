## 1. 板卡与固件（实测）

| 项 | 实际值 |
| --- | --- |
| 板卡 | 立创庐山派 Lite-K230D-CanMV，128MB |
| 固件 | `K230D-v1.8-0-gc2d1f5c` |
| 相机 | GC2093 定焦；模块换装过，现接 **CSI 2**（板子默认座子） |
| 通信口 | UART2（K230D 侧 GPIO11/12），GH1.25-4P 座，3.3V TTL |
| 存储 | 照片写 `/data`（可用约 6.5G），不写 `/sdcard`（仅剩约 107M） |
| 麦克风 | 板载麦克风正常，位于**右声道 ch1** |
| 扬声器 | FIT0502 **未接线**，播放功能当前不可用 |

CSI 拓扑实测：K230 有三路 CSI sensor 输入，`Sensor()` 不带 `id` 时解析到 CSI 2；`Sensor.list_mode(id=cid)` 是真实的逐总线 I2C 探测（空总线报 `Can not found sensor on CSI N`）。模式表按总线不同：**CSI 1 上限 60fps**（1920x1080@30/60、1280x960@60），**CSI 2 有 90fps 行**（1280x960@90、1280x720@90）。50Hz 目标下 CSI 1 没有余量，当前接 CSI 2 合适。

## 2. 已验证 / 未验证

**已实测：**

- 相机链路：720p 拍照录像、320×240 + OpenCV 约 **57 FPS**。
- 实时预览：32 秒 / 1920 帧，57.0–57.3 FPS，内存平稳，可正常停止。
- 每帧约 1.1KB 是**可回收垃圾而非泄漏**（五轮基准的起始内存完全一致）；画图 + 推流几乎不额外花帧率（bare 57.1 vs show 57.0）。循环内需定期 `gc.collect()`，否则堆攒满会来一次 full GC 造成帧间隔抖动。
- 相机模块换装后，现有脚本无需修改即可出图（默认模式与 1280x960@90 hint 均验证通过）。
- 黑边检测（PC 离线回放 328 帧）：主边界 ≥4 点出现率 **81%**，第二条边界 **2%**，拟合残差 p50 **7.9px**。
- 主控 20 字节结果包：用 `../control/tools/protocol_example.py` 复算 `../control/docs/protocol_v1_draft.md` 中的 3 个样例帧（`path_valid` / `start` / `stop`），**逐字节一致**；CRC 标准向量 `123456789` → `0x29B1` 一致。

**未验证，不能当成已完成：**

- 检测算法**未在板子上运行过**。`src/09_lane_track.py` 已移植、`py_compile` 通过，但 CanMV v1.8 是否提供 `find_blobs` / `get_statistics` / `density()` 尚未确认。
- 端到端 `processing_ms` **没有实测值**。协议中 100ms 是启动/保持运行的门槛，目前是未知数，不是已达标。
- 81% 是**桌面数据集**结果，不是场地命中率。桌面集含房间杂波（走廊、显示器、鞋、盒子），部分检测锁在房间暗边上。
- 相机模块换装后未重做 V-01 三距离标定；`OFF`、地平线参数、行↔距离对照表都需重测。
- 语音唤醒（KWS）未测；自定义命令词的模型与 assets 在板子和主机均缺失。
- 无 UART 发送端代码，视觉→主控**没有一次真实互通记录**。

## 3. 检测方案与参数

采用 `PORTING_REVIEW.md` 推荐首版架构中的**横向窄带方案**（该文档建议比较"修复后的八邻域追边"与"下部区域 6–10 条横向窄带检测"，视觉侧实现的是后者）：

```text
ROI 分块（9 块 × 22px，自 y=40 起）
  → 每块 thr = mean(tile) − OFF(22)    # 相对阈值，抗自动曝光漂移
  → 连通域 → 形状过滤（面积/高度/宽度/密度）
  → 倾斜地平线拟合，剔除墙上暗带
  → 自下而上贪心关联成两条边界 → 直线拟合
```

参数：`TILE_TOP=40, TILE_H=22, TILES=9, OFF=22, DARK_FRAC_MAX=0.45, MIN_AREA=60, MIN_H=10, MAX_W=130, MAX_DENSITY=0.75, LINK_TOL=38, HORIZON_MARGIN=6`。同一组数值内联在 `src/09_lane_track.py`（板端）与 `src/pc_lane_calib.py`（PC 端）两处；`src/vision_params.py` 是本次所用参数的快照，并附 CanMV v1.8 固件缺口清单，不被脚本 import，改参数时要同步那两处。换场地通常只调 `OFF`（场馆建议区间 18–30）。

该方案符合审查文档的两条约束：不对全图所有黑色区域做一次直线拟合（避免左右边界、终点虚线、阴影混在一起）；用相对阈值而非绝对灰度门限。

**与审查文档的一处偏离需说明**：文档建议"先用 192×120 灰度图，需要分辨细黑边时再评估 320×240"。视觉侧当前用 **320×240**，原因是黑色胶带远距离很细，192×120 下细边样本不足。该偏离待板级耗时实测后判断是否值得——若 `processing_ms` 吃紧，回退 192×120 是首选优化项。

## 4. 当前阻塞（视觉侧最高优先级）

**桌面 328 帧实测：一条车道边界出现率 81%，第二条只有 2%。**

原因不是算法，是几何：镜头高约 140mm、下俯约 25° 时，50cm 宽车道的远侧边界在 y≈120 以下进不了画面。

`PORTING_REVIEW.md` 已预见单侧失线并给出缓解口径："单侧失线时，可用已标定的'每行车道宽度'短时估计中线，并明确降低置信度；不能用全图固定像素宽度，更不能无限沿用上帧路径。"

需要决定（硬件 + 主控）：

| 方案 | 代价 | 影响 |
| --- | --- | --- |
| A. 改安装：加高或减小俯角，让两条边界同框 | 需重开孔位，受整机高 ≤180mm 约束 | 视觉侧优先希望这样 |
| B. 接受单边：一条边界 + 拟合斜率推方向，按审查文档用车道宽度短时估中线并降置信度 | 不改硬件 | 精度依赖斜率，主控控制环需放宽容错 |

该决定不做，`error` 和 `bend` 就没有稳定来源，协议对齐也无法产生可用数据。已作为待确认项登记在状态表 **D-09**。

## 9. 安全与约束（沿用，不变更）

- K230D 不接 2S 宽压 8V；Type-C `USB5V_IN` 与 40pin 排针 2/4 脚只能 5V。板上丝印 `12V GND 1A` 的 GH1.25-2P 是独立 8–24V ≤1A 输入，与该路不得互串，一次只走一路供电。
- UART GH1.25-4P 为数据线：5V 线不接并绝缘，TX/RX 交叉，共地，3.3V TTL。
- FIT0502 差分输出，两根线都不接地。
- 无 IMU、侧向红外、Pico、SU-03T；视觉是唯一循迹传感器，不自行增加硬件。
- 不改 BOM、引脚、协议字段；变更先经主控与硬件确认。
